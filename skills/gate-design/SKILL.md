# gate-design — 技術方針・設計判断

`gate-story` が決めるのは「何を・なぜ(What/Why)」、このスキルが決めるのは「どう作るか(How)」。**Story自体は技術的都合と疎結合であるべき**で、技術選定・アーキテクチャ判断はすべてここに属する。旧来の「大きな機能だけ重い設計フェーズを通す」という逃げ道は採らない——このフェーズは常に通過するが、自明なストーリーなら内容は数行で済ませてよい。

## 前提チェック

`.specs/stories/<slug>/STORY.md` が存在しない場合は、先に `gate-story` を完了させるようユーザーに促す。

## 手順

1. `STORY.md`(Gherkin Scenario含む)と、対象プロジェクトの既存コード・構成を読む。
2. **gate-architect** サブエージェント(Agent tool)に、STORY.mdの内容とプロジェクトの技術スタック・既存パターンの要約を渡して技術方針の起草を依頼する。複数の妥当な選択肢がある場合はトレードオフ込みで比較させる。
3. 影響が大きい判断は、`.specs/PERSONAS.md` のロスターからtech-lead・security-engineer・performance-analyst等、関連しそうなペルソナに `persona-agent` で一言レビューさせる(既存の複数ペルソナ機構を軽量に使う。フルラウンドの討議は必須ではない)。
4. `.specs/stories/<slug>/DESIGN.md` を書く(自明なストーリーなら簡潔に、数行でもよい)。
5. `.specs/stories/<slug>/STORY.md` のステータスを更新する。
6. 次は `gate-plan` に進むことを案内する。

## DESIGN.md フォーマット

```markdown
# Design: <ストーリータイトル>

## 採用する技術方針
選んだ方針と理由。

## 検討した代替案(あれば)
...

## 主要な技術判断
- 判断: ... / 理由: ... / トレードオフ: ...

## 変更対象ファイル・モジュール(概観)
- ...

## リスク・懸念事項
- ...

## ペルソナからの一言レビュー(実施した場合)
- tech-lead: ...
```
